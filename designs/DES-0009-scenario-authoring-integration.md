## 1. 目的と全体像

蠱毒の間に脚本制作機能（authoring / game-export）を追加し、ゲーム制作WebUI
（novel_mvp）と連携する。その連携面の責務・ID仕様・受け渡し方式・実装順を確定する。

上位概念（付録A・ネオン構想）：**脚本は媒体非依存の共通原液**であり、
1本の正本から 漫画／ゲーム／動画／4コマ へ展開する。

```
蠱毒の間（執筆・改稿・承認・履歴）        下流の各媒体
  scenes/SCN-xxxx.md（正本）
        │ game-export（決定論コード）
        ▼
  <作品>/inbox_authoring/scn_xxxx.md ──→ novel_mvp WebUI ──→ Godot / Ren'Py / 動画
        （唯一の受け渡し面・md 1本のみ）
  ※漫画・4コマへの展開は蠱毒側の別アダプタの仕事（本設計書のスコープ外）
```

本設計書が確定するのは **蠱毒→WebUI の連携面のみ**。蠱毒内部の実装可否（Q1）は
未調査であり、Q1依存事項は§8に設問の形で保留する（推測で埋めない）。

## 2. 確定済み前提（動かさない柵）

1. **柵1**: 正本はID埋め込みMarkdown。JSONは常にmdから生成される成果物（LET-0009 §2）
2. **柵2**: event.jsonは凍結済みJSON仕様v1系に準拠。新情報は拡張フィールドで乗せる。
   **実証済み**: Godot実走14/14 PASS・未知トップレベル／stepフィールドは
   無視でなく**素通し保持**（逆連携に有利）。ただし**未知step型はnovel_mvp lintで
   FAIL＝export拒否**のため、拡張は必ずフィールド追加方式（新step型禁止）
3. **柵3**: ビートはWebUIの編集階層に持ち込まない。変換時の消費材（コマ分割候補等）
4. **柵4**: AI生成経路はルナール一本化。ID発行・変換・lint・差分は決定論コード（DEC-0017）
5. **音声キー不可侵**: `{event_id}__{Lxxx}` 形式は音声資産・export・store-sim搬入・
   lint検査7の全部が結線済み。蠍毒側IDでの置換は**絶対禁止**（調査Q4-4）
6. **event_id規約**: `^[a-z][a-z0-9_]*$`・event_id＝ファイル名stem・manifest突合で検収

## 3. 接続アーキテクチャ（調査Q2の採用）

4層（シーン／ビート／コマ／行）のうち、WebUI／JSONへ持ち込むのは**シーンと行の2層のみ**。

| 層 | 接続 |
|---|---|
| シーン | イベント1件（台本md 1ファイル＝event_id） |
| ビート | `## 舞台:` 行の**出力位置**で表現（＝コマ分割候補）。痕跡は `stage` の拡張フィールド `beat_id` のみ。**新記法は足さない** |
| コマ | 持ち込まない（WebUIが決定論算出済み・二重定義禁止）。`frame_id`/`koma_id` は送らない |
| 行 | `line`/`narration`/`se` ステップ |

- 「1ビート＝1コマに固定しない」は `## 舞台:` の置き方だけで表現できる（実測済み）
- 素材ID（背景・表情・SE）は**提案であって確定ではない**。未配置IDはlint WARNING。
  warningノイズ回避のため、確度の低い提案は `## 舞台:` に直書きせず `※`行提案とし
  人間がWebUIで割り当てる（調査Q7-7）

## 4. ID仕様（調査Q3・Q4＋本設計書の裁定反映）

| 対象 | md上の置き場 | JSON拡張フィールド | 改修 |
|---|---|---|---|
| シーンID | frontmatter `source_scene_id: SCN-0004`（＋`source_chapter_id`） | eventトップレベル `source_scene_id` | `build_event()` 透過出力を数行 |
| ビートID | `## 舞台: 背景=shop, ビート=B01` | `stage.beat_id` | `STAGE_KEY_MAP` に1行追加（`音楽=`前例と同型・逆写像も自動で通る） |
| 行の出典 | **mdに書かない**（裁定1＝B方式・内容ハッシュ突合） | （S5まで透過なし） | なし |

- `scene_id → event_id` 写像: `SCN-0004 → scn_0004`（小文字化・ハイフン→アンダースコア）。
  **蠱毒側が書き出し時に写像しファイル名を確定する**（裁定3＝A）。逆引きは
  `source_scene_id` で常に可能（Godotが保持することは実証済み）
- 既存イベントへの遡及付与は**不要**（拡張フィールドは全任意・前方互換）
- 原典§8の`@`記法は現行アダプタと全面衝突（実測・情報が1つも通らない）のため**不採用**。
  蠱毒の出力書式は現行書式（`## 舞台:`/話者行＋`「」`/`?選択:`/`!効果:`/`@効果音:`/`※`）とする

## 5. 連携MVP（調査Q5の採用）

**HTTP API・常駐監視・双方向同期は不要。新規APIゼロ**で組む。

```
蠱毒 scenes/SCN-0004.md（正本）
  │ game-export（決定論・写像とファイル名確定込み）
  ▼
<作品>/inbox_authoring/scn_0004.md      ← 唯一の受け渡し面（裁定7＝A）
  │ WebUI「取り込み」ボタン（新設はinbox一覧＋このボタンのみ）
  ▼
①旧event.json退避 → ②save_event_md（既存API・.bak自動）
  → ③convert → ④hash_diff→apply-diff（音声流用・陳腐化退避）
  → ⑤lint結果・warning表示（既存表示部を流用）
```

- ④の結線は**DES-0008で根治済み**（mdエディタ保存経路含む・裁定2＝B・既済）。
  取り込み経路の新設時はDES-0008のS-1同型（cmd_convert writeback同型化）に合わせる
- 台本mdの置き場は `scenario_events_md/`。Tyrano旧系統 `scenario_md/` は**書式非互換の
  別パーサ**のため厳禁（調査Q5-4）
- 逆方向（将来）: `export/{作品}/events/*.json` を蠱毒が読むだけ。novel_mvp側工事ゼロ

### 7-2. 裁定6の司令塔案（LET-0010の骨子・ネオン承認待ち）

**「正本移転プロトコル」＝正本は常に1本、ただし所在が工程で移る。**

- 執筆・改稿フェーズ: 蠱毒側 `scenes/SCN-xxxx.md` が正本
- **取り込み（handoff）実行の瞬間に正本がWebUI側 `scenario_events_md/` へ移転**。
  以後、蠱毒側の同シーンmdは「参照用スナップショット」であり編集凍結
- 再改稿したい場合: WebUI側の現行mdを蠱毒側へ**逆コピーしてから**改稿を再開
  （＝正本が蠱毒へ戻る。手動コピーで開始・S5で機械化候補）
- これにより「2本のmdが並立し片方だけ更新される」状態は**プロトコル上存在しない**

理由: B（WebUI→蠱毒の書き戻し経路の新設）は往復可能性の真の解だが工事が重く、
現段階の実需要（取り込み後の微修正はWebUIで完結する）に対して過剰。
C（WebUI本文編集禁止）はDES-0008で守った音声差分の実利を自ら殺す。
A改は現物を1行も変えずに柵1の「二重化しない」を運用規約で成立させる。
Bは将来玉として帳簿に残す。

### A-1. Q1調査の現在地

Q1「蠱毒の間へ `authoring` と `game-export` を追加可能か」は**現物調査未着手**。
完了しているのは構想整理と役割確定まで：蠱毒への脚本制作機能追加の方向性／
ゲーム制作WebUIとの責務分離／正本＝ID入りMarkdown案／JSON＝生成成果物案／
ゲームUI側は読み込み口へ工事を絞る案／AI生成経路のルナール一本化／
authoring＝制作・編集・承認・履歴管理／game-export＝ゲームUI向け変換。

未確認: 蠱毒のディレクトリ構成／モジュール境界／実保存形式／SQLiteとMarkdown正本の
現在の責務／Context Pack生成・参照経路／新規タブ追加の既存UI影響／authoringと
既存添削機能のデータ共有／game-exportの独立モジュール追加可否／必要回帰項目。

現時点の回答:「設計上は追加可能と見込むが、コード現物に基づく追加可否は未判定」。
Q1調査はポチの利用枠回復後または別施工担当確保後に読み取り専用で行う。

### A-2. 脚本＝複数媒体の共通原液

```text
脚本
├─ 漫画の元
├─ ゲームの元
├─ 動画の元
└─ 4コマ漫画の元
```

最初から長編を作らず「簡単なテーマから短い脚本を作り、数をこなす」を育成・検証の入口にする。

### A-3. 最初の訓練単位は4コマ

テーマ1行入力→4コマ規模の脚本を複数生成。
基本構造: 1コマ目=状況提示／2コマ目=展開／3コマ目=変化・ひねり／4コマ目=オチ・余韻。

```yaml
format: four_panel
theme: 雨の日、傘を忘れたメイド
beats:
  - beat_id: B01
    role: setup
    purpose: 外が土砂降りだと示す
  - beat_id: B02
    role: development
    purpose: 傘を忘れたことに気づく
  - beat_id: B03
    role: twist
    purpose: 主人公が傘を差し出す
  - beat_id: B04
    role: punchline
    purpose: キャラクター性のあるオチを付ける
```

### A-4. 同じ脚本から媒体別へ展開

- **4コマ漫画**: 1ビート原則1コマ。各コマへ背景・登場人物・表情・ポーズ・カメラ・
  吹き出し・台詞・視覚的オチを追加
- **ゲーム**: 4ビートを短いイベントへ展開（背景→台詞→表情変更→選択肢→反応→好感度変化）。
  固定展開を台詞・演出・選択肢・状態変化へ拡張
- **動画**: 4ビートを4カット程度へ変換。各カット秒数・音声・字幕・BGM・SE・カメラ移動・
  表情変化・カット間接続を追加。10〜30秒動画へ展開可能

### A-5. 数をこなす目的

4コマ規模なら一作品ごとの原因分析がしやすい。評価対象: 導入の理解可能性／2コマ目の進行／
3コマ目の変化／オチの予測可能性／キャラクター性／台詞の長さ／絵での成立／媒体変換可能性。
短編多数で失敗パターン・オチの型・キャラ別反応・絵映え構造・ゲーム向き展開・
動画向きテンポを効率蓄積。

### A-6. 1テーマから複数案生成

ルナールからA案（会話オチ）/B案（勘違いオチ）/C案（キャラ性オチ）等の複数案を生成。
人間が採用／部分採用／不採用・不採用理由・修正内容・修正理由を記録。
完成稿だけでなく「どの企画案をなぜ選んだか」という**選択ナレッジ**を蓄積。

### A-7. 蠱毒の間での循環

テーマ入力→ルナール複数生成→人間が選択・修正→修正理由と不採用理由を保存→
漫画・ゲーム・動画へ出力→実制作結果を評価→蠱毒ナレッジへ還元。
最終目的:「小さい脚本を大量に生成・比較・添削・実装し、複数媒体へ展開可能な
脚本生成能力を育てる」。

### A-8. 初期MVP候補
