## 1. 目的と全体像

蠱毒の間に脚本制作機能（authoring / **game-handoff**）を追加し、ゲーム制作WebUI
（novel_mvp）と連携する。その連携面の責務・ID仕様・受け渡し方式・実装順を確定する。

上位概念（付録A・ネオン構想）：**脚本は媒体非依存の共通原液**であり、
1本の正本から 漫画／ゲーム／動画／4コマ へ展開する。

```
蠱毒の間 authoring（正本・制作・改稿・承認・履歴）
  scenes/SCN-xxxx.md（脚本正本）
        │ game-handoff（受け渡しmd整形・事前検証・atomic publish・決定論）
        ▼
  <作品>/inbox_authoring/scn_xxxx.md ──→ novel_mvp WebUI ──→ Godot / Ren'Py / 動画
        （唯一の受け渡し面・md 1本のみ）      （md→event.json変換・演出・素材・
                                              音声・ゲーム実装）
  ※漫画・4コマ・動画向けの媒体別IRは蠱毒側の将来拡張（本設計書のスコープ外・
    ゲームのevent.json契約とは独立）
```

**三者の責務（LET-0013 §5で確定）**:
- 蠱毒の間＝脚本の正本・制作・改稿・承認・履歴
- game-handoff＝受け渡しmdの整形・事前検証・atomic publish
- ゲーム制作WebUI＝mdからevent.jsonへの変換・演出・素材・音声・ゲーム実装

**event.json生成責務はWebUIへ一本化**（LET-0011衝突1・相互承認済み）。
蠱毒側でevent.jsonは生成しない。DES-0001仕様追従・音声差分・lint・.bak結線は
WebUI既存経路へ集約する。

## 2. 確定済み前提（動かさない柵）

1. **柵1**: 正本はID埋め込みMarkdown。JSONは常にmdから生成される成果物（LET-0009 §2）。
   正本の所在規約は§7-2（LET-0013で確定）
2. **柵2**: event.jsonは凍結済みJSON仕様v1系に準拠。新情報は拡張フィールドで乗せる。
   **実証済み**: Godot実走14/14 PASS・未知トップレベル／stepフィールドは素通し保持。
   ただし**未知step型はnovel_mvp lintでFAIL＝export拒否**のため、拡張は必ず
   フィールド追加方式（新step型禁止・`inner_voice`等も追加しない）
3. **柵3**: ビートはWebUIの編集階層に持ち込まない。変換時の消費材
4. **柵4**: AI生成経路はルナール一本化。ID発行・変換・lint・差分は決定論コード（DEC-0017）
5. **音声キー不可侵**: `{event_id}__{Lxxx}` 形式は音声資産・export・store-sim搬入・
   lint検査7の全部が結線済み。変更禁止（LET-0013裁定4境界でも再確認）
6. **event_id規約**: `^[a-z][a-z0-9_]*$`・event_id＝ファイル名stem・manifest突合で検収

## 3. 接続アーキテクチャ（調査Q2の採用・確定）

4層（シーン／ビート／コマ／行）のうち、WebUI／JSONへ持ち込むのは**シーンと行の2層のみ**。

| 層 | 接続 |
|---|---|
| シーン | イベント1件（台本md 1ファイル＝event_id） |
| ビート | `## 舞台:` 行の**出力位置**で表現（＝コマ分割候補）。痕跡は `stage` の拡張フィールド `beat_id` のみ・**任意**（送らない運用も契約適合、送るなら `## 舞台: 背景=xxx, ビート=B01` の正書式一択。LET-0011 §2補足）。新記法は足さない |
| コマ | 持ち込まない（WebUIが決定論算出済み・二重定義禁止）。`frame_id`/`koma_id` は送らない |
| 行 | `line`/`narration`/`se` ステップ。**ID札は書かない**（裁定1・LET-0013裁定4境界） |

- 素材ID（背景・表情・SE）は提案であって確定ではない。未配置IDはlint WARNING。
  確度の低い提案は `## 舞台:` に直書きせず `※`行提案とし人間がWebUIで割り当てる
- 蠱毒の出力書式は現行書式（`## 舞台:`/話者行＋`「」`/`?選択:`/`!効果:`/`@効果音:`/`※`）。
  原典`@`記法は全面衝突（実測）のため不採用

## 4. ID仕様（final）

| 対象 | md上の置き場 | JSON拡張フィールド | 改修 |
|---|---|---|---|
| シーンID | frontmatter `source_scene_id: SCN-0004`（＋`source_episode_id`） | eventトップレベル `source_scene_id` | `build_event()` 透過出力を数行 |
| ビートID | `## 舞台: 背景=xxx, ビート=B01`（任意） | `stage.beat_id` | `STAGE_KEY_MAP` に1行追加（逆写像も自動） |
| 行の出典 | **mdに書かない**（裁定1・内容ハッシュ突合） | なし（S5まで透過なし） | なし |

**写像（裁定3・final・LET-0013 §1）**: `SCN-0004 → scn_0004`
- 英字小文字化・ハイフン→アンダースコア。event_id＝受け渡しmdファイル名stem
- **写像責務は蠱毒側game-handoffが持つ**。写像結果はhandoff実行前previewで人間確認可
- 元のscene_idはfrontmatter `source_scene_id` として保持（逆引き恒久維持）
- **WebUI側はevent_idの再採番・再写像を行わない**。取り込み時の検算
  （写像規則の再計算一致検証）は行うが、検証のみで改名はしない
- 不正形式・既存event_id衝突時は**handoffを失敗させる**。自動別名付与で回避しない
- 既存イベントへの遡及付与は不要（拡張フィールドは全任意・前方互換）

**蠱毒内部ID**: beat_id/line_id/proposal_id等の内部管理・型付き連番・UUID運用は
ネオン裁量（受け渡し面に出さない限り本設計書は関知しない）。蠱毒内部の
export対応表（internal_line_id/exported_text_hash/source_commit/export_revision）は
内部派生データであり受け渡し対象外（LET-0012 §2）。

**心の声（裁定4・final・LET-0013 §2）**: speaker名方式。
```md
みなみ（心の声）
「本当に、この店を続けられるのかな……」
```
- 「（心の声）」サフィックスを蠱毒側出力テンプレの正書式として規約化
- frontmatter characters・音声配役に登録（同キャラ同ボイスの別演技として配役可能）
- authoring内部でのline_type等の意味情報保持は自由。受け渡し面ではspeaker名へ畳み込む
- narrationへ変換しない・新step型を追加しない・音声キー規則を変更しない
- 将来の専用表示効果・音声加工は本契約を変えずWebUI側の演出設定として拡張

## 5. 連携MVP（final）

### 5-1. 経路

**HTTP API・常駐監視・双方向同期は不要。新規APIゼロ**で組む。

```
蠱毒 scenes/SCN-0004.md（脚本正本）
  │ game-handoff（写像・整形・事前parser/lint・preview・atomic publish）
  ▼
<作品>/inbox_authoring/scn_0004.md      ← 唯一の受け渡し面（裁定7）・配送面であり正本ではない
  │ WebUI「取り込み」ボタン（新設はinbox一覧＋このボタンのみ）
  ▼
①旧event.json退避 → ②save_event_md（既存API・.bak自動）
  → ③convert → ④hash_diff→apply-diff（音声流用・陳腐化退避）
  → ⑤lint結果・warning表示（既存表示部を流用）
```

- ④の結線はDES-0008で根治済み。取り込み経路新設時はDES-0008のS-1同型に合わせる
- 台本mdの置き場は `scenario_events_md/`。Tyrano旧系統 `scenario_md/` は厳禁（別パーサ）
- 逆方向（将来）: `export/{作品}/events/*.json` を蠱毒が読むだけ。novel_mvp側工事ゼロ

### 5-2. handoffファイルの更新規則（LET-0013 §4で確定）

- 同一scene_id・source hash同一なら再出力はno-opでよい
- source hashが異なる場合のみ新しいhandoffとして更新。一時ファイル生成後の
  **atomic replace**
- source commit・source hash・export revisionは蠱毒内部へ記録
- WebUI側の取り込みは既存の退避・差分・lint経路を**必ず**通す
- inbox上のファイル更新だけで正本移転完了とは見なさない
- 配送失敗・WebUI取り込み失敗時も蠱毒側の脚本正本mdは変更しない

### 7-2. 正本所在規約（裁定6 final・LET-0013 §3の確定内容）

LET-0010原案「取り込み時にWebUIへ正本移転」はネオン回答により改良され、
以下で確定した。**原則：脚本本文の正本は常に1本・所在は明確・移転は人間承認**。

**(a) authoring導入後の新規シーン**
- 蠱毒側の脚本md＝正本／inbox_authoring内のmd＝受け渡し用派生物／
  WebUIへ取り込まれたmd・event.json＝ゲーム実装用派生物
- inbox_authoringやWebUI側のmdを独立した第二の正本にはしない

**(b) authoring導入前から存在する既存シーン**
- 自動的に正本を移転しない。明示的な移転完了までは従来の正本（WebUI側
  `scenario_events_md/`）を維持＝**現行運用は無変更**
- 移転はシーン単位・以下10条件を満たすこと：①対象シーンの人間指定
  ②現正本ファイルとGitコミットの記録 ③移転作業中の新旧同時編集禁止
  ④既存内容のauthoring取り込み ⑤scene_id等固定情報の維持 ⑥authoring側で
  確定md保存 ⑦game-handoffで受け渡しmd生成 ⑧WebUI既存アダプタで取り込み
  ⑨lint PASS・想定外差分ゼロ確認 ⑩人間承認後にのみ正本所在を切替
- 移転完了前に問題発生時は正本切替を行わない。旧正本維持・途中生成物は
  未確定データとして破棄or隔離。部分的な正本移転状態を残さない

**(c) 移転後の境界**
- 脚本本文の変更＝authoring側
- WebUI側の責務＝演出（背景・立ち絵・BGM・SE・コマ割り・表示タイミング・
  音声・ゲーム固有演出）
- WebUIのmdエディタで本文を編集した場合、それは**作業コピーの編集**であり
  正本には反映されない。本文へ戻すべき変更は将来の逆連携（S5）または
  人間によるauthoring反映を通す。WebUI変更をauthoring正本へ自動上書きしない

**(d) 禁止事項**
正本の自動一括移転／人間承認なしの正本切替／脚本本文の双方向自動同期／
同一本文の二か所同時正本編集／移転失敗時の旧正本削除・改名／
既存SC-0012の無条件移動・自動変換／SQLiteだけを正本とすること。
SC-0012は後方互換fixtureとして維持、移転は別途明示承認。

### A-2. 脚本＝複数媒体の共通原液

```text
脚本
├─ 漫画の元
├─ ゲームの元
├─ 動画の元
└─ 4コマ漫画の元
```

最初から長編を作らず「簡単なテーマから短い脚本を作り、数をこなす」を育成・検証の入口にする。

### A-3. 最初の訓練単位は4コマ

テーマ1行入力→4コマ規模の脚本を複数生成。
基本構造: 1コマ目=状況提示／2コマ目=展開／3コマ目=変化・ひねり／4コマ目=オチ・余韻。

```yaml
format: four_panel
theme: 雨の日、傘を忘れたメイド
beats:
  - beat_id: B01
    role: setup
    purpose: 外が土砂降りだと示す
  - beat_id: B02
    role: development
    purpose: 傘を忘れたことに気づく
  - beat_id: B03
    role: twist
    purpose: 主人公が傘を差し出す
  - beat_id: B04
    role: punchline
    purpose: キャラクター性のあるオチを付ける
```

### A-4. 同じ脚本から媒体別へ展開

- **4コマ漫画**: 1ビート原則1コマ。各コマへ背景・登場人物・表情・ポーズ・カメラ・
  吹き出し・台詞・視覚的オチを追加
- **ゲーム**: 4ビートを短いイベントへ展開（背景→台詞→表情変更→選択肢→反応→好感度変化）。
  固定展開を台詞・演出・選択肢・状態変化へ拡張
- **動画**: 4ビートを4カット程度へ変換。各カット秒数・音声・字幕・BGM・SE・カメラ移動・
  表情変化・カット間接続を追加。10〜30秒動画へ展開可能

### A-5. 数をこなす目的

4コマ規模なら一作品ごとの原因分析がしやすい。評価対象: 導入の理解可能性／2コマ目の進行／
3コマ目の変化／オチの予測可能性／キャラクター性／台詞の長さ／絵での成立／媒体変換可能性。
短編多数で失敗パターン・オチの型・キャラ別反応・絵映え構造・ゲーム向き展開・
動画向きテンポを効率蓄積。

### A-6. 1テーマから複数案生成

ルナールからA案（会話オチ）/B案（勘違いオチ）/C案（キャラ性オチ）等の複数案を生成。
人間が採用／部分採用／不採用・不採用理由・修正内容・修正理由を記録。
完成稿だけでなく「どの企画案をなぜ選んだか」という**選択ナレッジ**を蓄積。

### A-7. 蠱毒の間での循環

テーマ入力→ルナール複数生成→人間が選択・修正→修正理由と不採用理由を保存→
漫画・ゲーム・動画へ出力→実制作結果を評価→蠱毒ナレッジへ還元。
最終目的:「小さい脚本を大量に生成・比較・添削・実装し、複数媒体へ展開可能な
脚本生成能力を育てる」。

### A-8. 初期MVP候補

1. テーマ1行入力 2. キャラ選択 3. ジャンル選択 4. 4コマ脚本3案生成 5. 採用案選択
6. 台詞・展開編集 7. 採用/不採用理由保存 8. 各コマの背景・表情・構図提案
9. 確定脚本として保存 10. 出力先選択（4コマ漫画/ゲーム/動画）。
初期実装は生成・比較・添削・保存までに絞ってよい。ゲーム・動画への本格出力は後段でも、
**正本データには媒体非依存のビート構造を保持しておく**。
