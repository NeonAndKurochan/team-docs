# LET-0002：部隊間共有ルール（letters運用規約）草案r2

発行者：司令塔マックス
宛先：ネオン
date：2026-07-23
status：proposed

本書は、司令塔部隊と創作部隊の双方が応答レターで承認し、
decisions.mdへ合意を記録した時点で発効する。

## 1. 原則

- letters/は、部隊間の通知・依頼・応答・相互合意を正式に成立させる
  唯一のチャネルとする。
- チャットでの会話や先輩による口頭配達は、相談・予告・催促には使えるが、
  letters/へ確定文書が置かれるまでは正式共有・相互拘束とは見なさない。
- 設計書や成果物の正本は、designs/または各担当リポジトリに置いてよい。
  letters/には正本を複製せず、必要に応じて対象文書・パス・コミットを記載する。
- 境界の共通ルールは本書で定める。
  各部隊内部の文書作成方法、使用ツール、作業手順には相互干渉しない。
- 各部隊は自分が発行する文書のみ新規作成する。
  相手が発行したレターは読み取り専用とし、編集・削除・改名しない。

## 2. ファイル形式

- 命名は `LET-XXXX-題名.md` とする。
- XXXXはゼロ埋め4桁で、既存最大番号+1を採番する。
- 同時発行により番号が衝突した場合は、まだGit確定されていない側が
  次番号へ変更する。確定済みレターは改名しない。
- 冒頭には以下を記載する。

  - id
  - 発行者
  - 宛先
  - date
  - status

- 必要に応じて以下を追加する。

  - in_reply_to
  - response
  - supersedes
  - source

- statusは文書発行時の性質を表す。

  - proposed：相手の判断・応答を求める提案
  - final：発行者の担当範囲における確定通知
  - report：報告
  - request：作業依頼

- 発行済みレターは上書きしない。
- 提案への承認・拒否・条件付き承認は、宛先側が新しい応答レターとして発行する。
- 旧文書を置き換える場合は、旧文書を書き換えず、
  新文書側へ `supersedes: LET-XXXX` と記載する。

## 3. 置く・応答するタイミング

- 次の場合にレターを置く。

  - 相手部隊の作業へ影響する仕様・裁定
  - 相互承認が必要な事項
  - 正式な作業依頼
  - 工程クローズや基準版確定などの重要な節目
  - 相手側に記憶されていないと認識漏れが起きる事項

- 宛先側は、原則として次に自側の作業を行う際に応答する。
- 緊急時は先輩がチャットで催促してよいが、正式な応答はレターへ残す。
- 各部隊は、先輩の承認を自分の会話内で得てからレターを発行する。
- 相互拘束事項は、提案レター・応答レター・decisions.mdの記録が
  揃った時点で発効する。

## 4. 既存棚との関係

### decisions.md

- 相互合意した裁定の索引とする。
- 1裁定につき、DEC番号・件名・根拠レターID・発効日を1行で記録する。
- 詳細本文はレターまたは参照先の設計書を正とする。
- 合意を覆す場合は過去行を削除せず、新しいDECを追加する。

### board.md

- 各部隊の現在地を共有する非拘束の掲示板とする。
- 原則として、着工・工程クローズ・BLOCKED発生・重要な待ち状態の変更時に更新する。
- 各欄には更新者と更新日を記載する。
- 更新日の古い情報は、現在も有効であることを保証しない。
- 正式な仕様・裁定・依頼の根拠には使用しない。

### designs/

- repoを持たない設計書の正本を置く。
- レターから設計書を参照する場合は、ファイル名またはパスを明記する。

## 5. LET-0001との関係

- 本書はLET-0001全体を破棄または上書きしない。
- LET-0001 §1の蠱毒の間からteam-docsへのexport構想は、
  具体的な共有対象・継続需要・別途施工承認が揃うまで未着手・休眠とする。
- export口の新設は、本書の発効だけを根拠として自動着工しない。
- 必要性が生じた場合は、別レターで対象文書・目的・施工範囲を提案し、
  相互承認後に着工する。
